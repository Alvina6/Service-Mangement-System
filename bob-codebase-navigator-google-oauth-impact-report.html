01Feature Understanding

"Add Google OAuth authentication" means users can sign in (and implicitly register) using their Google account instead of — or in addition to — an email/password pair. Google's OAuth 2.0 flow issues a signed Google ID token to the browser, which the backend exchanges for a verified user profile (name, email, Google subject ID) and then issues a standard ServiceFlow JWT in the same shape the rest of the application already consumes.

For this codebase the most practical strategy is the client-side credential flow (using @react-oauth/google): the Google popup runs entirely in the browser, returns an ID token, and the frontend POSTs that token to a new backend route (POST /api/auth/google) which verifies it with google-auth-library. No server-side session or Passport.js is required.

The backend then performs a find-or-create (upsert) against the User collection — returning an existing user if the email or googleId already exists, or creating a new customer-role user otherwise — and calls the already-present generateToken(user._id) helper to issue the ServiceFlow JWT. From that point on, every downstream layer is unchanged: the same localStorage key, axios interceptor, protect middleware, and role-based dashboards all work transparently.

08Risks
Risk 1 — Blocker: password: required:true (Confirmed)

backend/models/User.js:9 — Mongoose validates required: true before the pre-save hook runs. Any User.create() call for an OAuth user without a password will throw a ValidationError. This is a silent hard blocker that produces no obvious OAuth-related error message. Must be fixed first.

Risk 2 — Account Linking Collision (Confirmed)

A user who registered with email+password and later signs in with Google using the same email will trigger a MongoDB E11000 duplicate-key error (email is unique: true) if the OAuth controller naively calls User.create() without a prior lookup. The controller must perform User.findOne({ email }) first, link the googleId to the existing account, and return a new JWT rather than rejecting with "email already in use."

Risk 3 — generateToken is module-private (Confirmed)

generateToken is defined as a non-exported const in authController.js. It is reusable within the same file, but if the OAuth handler is placed in a separate file, it must either be moved to a shared utility or duplicated. Recommend adding the OAuth handler to the existing authController.js to avoid this issue.

Risk 4 — comparePassword on OAuth Users (Confirmed)

userSchema.methods.comparePassword calls bcrypt.compare(candidate, this.password). If this.password is undefined for an OAuth-only user, bcrypt will throw or return false. If any code path ever calls comparePassword on an OAuth user, this will produce a cryptic error. The login controller should short-circuit if user.googleId is set and no password is stored.

Risk 5 — Helmet CSP may block Google Identity SDK (Potential)

backend/server.js:30 — Helmet's default Content-Security-Policy does not include accounts.google.com in allowed script/frame sources. The @react-oauth/google library loads an external JS snippet from Google. This may be blocked in production. The backend's helmet() config or Next.js's next.config.mjs headers would need a script-src allowance.

Risk 6 — JWT in localStorage (XSS Exposure, Pre-existing)

This is not introduced by OAuth but is amplified by it. The Google sign-in surface increases the JavaScript exposure of the page. A stored XSS attack could exfiltrate the serviceflow_token from localStorage. This is a known architectural trade-off; HttpOnly cookies would mitigate it but require significant changes to AuthContext, the axios interceptor, and the backend CORS config. Document as a known risk.

Risk 7 — Zero Test Coverage (Critical, Pre-existing)

No automated tests exist. Any regression in the auth flow — schema changes, route additions, middleware interaction — is detectable only through manual QA. The password: required change, the upsert logic, and the new route are all untestable without a test framework being installed first.

09Missing Information & Unknowns
Google Cloud Project credentials not yet obtained. A Google Cloud Console project with an OAuth 2.0 client ID, consent screen configured, and authorized redirect/origin URIs must be created before any implementation can be tested. This is an external prerequisite with no in-codebase signal of prior setup.
Account-linking policy undefined. It is currently unspecified whether a user who previously registered with email+password and then signs in with Google using the same email should: (a) have their accounts linked silently, (b) be prompted to link accounts, or (c) receive an error. The implementation choice affects the googleAuth controller logic significantly.
Staff accounts via Google OAuth. The current design only supports customer role for public sign-ups. It is unclear whether dispatchers or admins should ever be able to use Google OAuth. If so, the admin-only POST /api/auth/staff flow would need an OAuth variant. Assumed out-of-scope until confirmed.
Token refresh strategy. The current JWT expires in 7 days (JWT_EXPIRES_IN). When a ServiceFlow JWT expires for a Google OAuth user, they must click "Sign in with Google" again. There is no silent token refresh mechanism. If seamless re-authentication is required, a refresh-token flow or silent re-authorization with Google's SDK would be needed — this is not currently designed for either auth method.
Production redirect URI. The Google OAuth authorized redirect URI must match exactly. The backend GOOGLE_CALLBACK_URL env var must be set correctly for both local development and production environments. This value is not yet documented anywhere in the codebase.
presentation.md content was unread prior to investigation. Now confirmed: Slide 9 lists Google Maps API as a future roadmap item but makes no mention of Google OAuth. This means OAuth was not on the original project roadmap and stakeholders may need to be briefed on the new dependency on Google Cloud Console.
10Proposed Implementation Plan

The following steps are ordered to eliminate blockers first, introduce backend before frontend, and add tests alongside each change. No step should be executed until the developer approves the plan.

  1. Prerequisites — Google Cloud Console Setup (External)
    Create a Google Cloud project → enable the Google People API → configure OAuth consent screen (External, scopes: email, profile) → create OAuth 2.0 Client ID (Web Application type) → note Client ID and Client Secret → add authorized JavaScript origins (http://localhost:3000) and authorized redirect URIs (http://localhost:5000/api/auth/google/callback if redirect flow; not needed for ID-token flow).
  2. Install Dependencies
    Backend: npm install google-auth-library. Frontend: npm install @react-oauth/google. Also install test infrastructure: backend npm install -D jest supertest mongodb-memory-server, frontend npm install -D jest @testing-library/react @testing-library/jest-dom. Add "test": "jest" to both package.json scripts.
  3. Fix User Schema — Remove password Required Blocker
    In backend/models/User.js: change password field to required: function(){ return !this.googleId; }. Add googleId: { type: String, sparse: true, unique: true } field. Write unit tests in backend/models/User.test.js to verify: (a) create without password + with googleId succeeds; (b) create without password + without googleId fails validation; (c) pre-save bcrypt hook is skipped safely when password is undefined.
  4. Add googleAuth Controller Function
    In backend/controllers/authController.js: add const { OAuth2Client } = require('google-auth-library') at top. Add exported googleAuth async function: verify ID token → extract payload (email, name, sub/googleId, picture) → User.findOne({ googleId }) → if not found, try User.findOne({ email }) (account linking) → if still not found, User.create({ name, email, googleId, avatarUrl: picture, role: 'customer', isActive: true }) → call existing generateToken(user._id) → return { success: true, user: user.toSafeObject(), token }. Handle Google verification errors with 401. Write unit tests with google-auth-library mocked.
  5. Register New Route
    In backend/routes/authRoutes.js: import googleAuth. Add router.post('/google', googleAuth). No protect middleware — user is unauthenticated. Write integration test via supertest: POST with mocked valid/invalid Google token → assert correct responses.
  6. Update Environment Files
    Add to backend/.env.example: GOOGLE_CLIENT_ID=, GOOGLE_CLIENT_SECRET=. Add to frontend/.env.local.example: NEXT_PUBLIC_GOOGLE_CLIENT_ID=. Add actual values to backend/.env and frontend/.env.local (not committed). Update README.md with Google Cloud Console setup steps and new env var inventory.
  7. Add loginWithGoogle to AuthContext
    In frontend/src/context/AuthContext.js: add const loginWithGoogle = async (idToken) => { const res = await api.post('/auth/google', { idToken }); localStorage.setItem('serviceflow_token', res.data.token); setUser(res.data.user); return res.data.user; }. Add loginWithGoogle to the Provider value. Write RTL tests for success and error paths.
  8. Wrap App in GoogleOAuthProvider
    In frontend/src/app/layout.js (or a "use client" wrapper component): wrap <AuthProvider> with <GoogleOAuthProvider clientId={process.env.NEXT_PUBLIC_GOOGLE_CLIENT_ID}>. Since layout.js is a server component in Next.js 14, create a frontend/src/components/Providers.jsx client component that composes both providers, then use it in layout.js.
  9. Add Google Button to Login Page
    In frontend/src/app/login/page.js: import GoogleLogin from @react-oauth/google. Add the button below (or above) the password form with an onSuccess={async ({ credential }) => { const user = await loginWithGoogle(credential); router.push('/dashboard/' + user.role); }} handler and an onError handler that sets the error state. Write RTL test for render + success redirect + error display.
  10. Add Google Button to Register Page (UX consistency)
    In frontend/src/app/register/page.js: same as step 9, but redirect on success goes to /dashboard/customer (all OAuth sign-ups are customers). This is optional if the login page's upsert handles first-time users, but recommended for UX.
  11. Update Documentation Files
    Update er_diagram.md (add googleId to User entity, mark password optional), system_flow.md (add OAuth branch), README.md (prerequisites, new env vars, new API endpoint), nixpacks.toml (add env var comment), backend/seed.js console log (clarify password-only seeding).
  12. Verify Helmet CSP in Development and Production
    Test that the @react-oauth/google button renders without CSP violations. If blocked, add scriptSrc: ["'self'", "accounts.google.com"] and frameSrc: ["accounts.google.com"] to the helmet configuration in backend/server.js, or add equivalent headers in frontend/next.config.mjs. This step is exploratory — only needed if CSP violations are observed.
